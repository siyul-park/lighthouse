# Tool reference

Generated by `lighthouse docs generate` from the tool definitions; `lighthouse docs check` fails when it is stale.

`lighthouse mcp` serves the commands an agent uses in the loop as Model Context Protocol tools. A tool is named by the path of its command joined by `_`, takes the long flags of the command in camelCase and returns the command's `--format json` output as `structuredContent`, with the same JSON in a text block. A failure is a result with `isError: true`; an unknown tool is a protocol error. Housekeeping and setup (`review prune`, `cache clean`, `spec validate`, `schema`, `docs`, `init`, `trust`, `mcp`, `hook`, `completions`) are not tools.

## check

Check the project and print findings.

PATHS select which findings are reported, not what is analyzed: the whole project is always analyzed, because decisions and language providers need more than the reported files (callers, packages, build context).

Exit codes: 0 clean, 1 an error was found (or warnings fail the run: --strict, --max-warnings; info never does), 2 usage or runtime error, 3 the analysis was incomplete (a file could not be read or loaded, a plugin crashed or timed out). "Not checked" is never "passed"; --allow-incomplete reports it but does not fail on it.

Plugins named by the config are started and run with your privileges, like build scripts: only check projects whose config you trust. A plugin that cannot start, or that is not the protocol version or identity its entry names, is an error (exit 2); one that starts but crashes, times out or answers badly is reported as incomplete (exit 3).

Examples:
  lighthouse check
  lighthouse check src/ --decision 'design/*' --format json --limit 10
  lighthouse check --changed --strict
  lighthouse check --fix --dry-run --decision design/exported-doc

Result: [CheckReport](../schema/check-report.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `allModels` | boolean | `false` | Ask models that cost about the whole project, not only the files the run reports. |
| `allowIncomplete` | boolean | `false` | Exit by findings even when the analysis was incomplete; the incompleteness is still reported. |
| `changed` | boolean | `false` | Report only files changed in the working tree against HEAD (modified, added, renamed, untracked). A report filter like PATHS. |
| `decision` | string[] | `[]` | Run only these decisions: ids, comma-separated or repeated, and globs such as `design/*`. |
| `detail` | compact \| full | `"compact"` | With `--format json`: compact groups findings by decision and states a decision's text once; full gives one self-contained record per finding. |
| `diff` | string \| null | `null` | Report only files changed since the merge base of BASE and HEAD, including the working tree and untracked files. A report filter. |
| `limit` | integer \| null | `null` | Report at most this many findings, errors first, and say how many were left out. Default: 25 with `--format json`, all otherwise. |
| `maxWarnings` | integer \| null | `null` | Fail when there are more than N warnings (errors always fail). |
| `noCache` | boolean | `false` | Run every rule instead of reusing the findings of earlier runs kept in `.lighthouse/cache`. The findings and the exit code are the same. |
| `noModels` | boolean | `false` | Ask no model: what they would judge is left to review. |
| `noStore` | boolean | `false` | Do not record this run in `.lighthouse/lighthouse.db` and do not apply judgments. By default a run is recorded: findings it no longer reports are marked resolved (never when the analysis was incomplete), and findings whose latest judgment hides them stay out of the report. |
| `paths` | string[] | `[]` | Where to report findings; the whole project is analyzed anyway. Default: the whole project. |
| `recordModelLabels` | boolean | `false` | Record what models fail as judgments attributed to them, so that training can reproduce them from `decisions.jsonl`. |
| `strict` | boolean | `false` | Fail on warnings too. |

## fix

Fix findings with the fixers their decisions name.

Fix findings with the fixers the decisions name (`fix` in `decision_list`: who makes it, `safe` or `unsafe`, whether it runs). Select what to fix with `fingerprints` (findings from `check`, prefixes of at least 7 characters allowed), `paths` or `decision`; at least one is required. A fix is proposed, applied, re-checked (the safe fixes of what it introduced follow it) and rolled back for any file that gains an error or stops being analyzed, and repeated until nothing is left (at most 5 rounds). Only `safe` fixes are written, whatever makes them; an `unsafe` one is returned as a preview with its diff and the call that applies exactly it (`fingerprints` of every finding of its run, with `unsafeFixes`), unless `unsafeFixes` is true or, when it is not set, the project's `[fix] unsafe` is true; `unsafeFixes: false` only previews. Applying a preview writes exactly the edit that was shown, kept by the run that made it: a file that changed since gives a conflict and writes nothing, and a preview that is not kept is declined. `noModels` asks no model. Use `dryRun` first to see the unified `diff` without changing a file. Returns the `diff`, the `applied` fixes, the `previews` and the `declined` findings with the reason each was left alone; recheck with `check` afterwards. Findings a judgment hides are never fixed.

Result: [FixReport](../schema/fix-report.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `decision` | string[] | `[]` | Fix the findings of these decisions: ids or globs. |
| `dryRun` | boolean | `false` | Print the unified diff and leave every file as it was. |
| `fingerprints` | string[] | `[]` | Fix these findings: fingerprints or unique prefixes of at least 7 characters. |
| `fixer` | string \| null | `null` | Use this registered fixer for the selected findings instead of the one their decision names. Its fixes are `unsafe`. |
| `noModels` | boolean | `false` | Ask no model: what they would fix is left to review. |
| `paths` | string[] | `[]` | Fix findings under these paths. |
| `unsafeFixes` | boolean \| null | `null` | Write `unsafe` fixes, which are judgment calls, whatever makes them (`true`), or only preview them (`false`); unset, `[fix] unsafe` decides. A preview is applied by naming its finding. |

## decision_create

Add a project-local decision from a Decision document.

The document is YAML or JSON, from a file or stdin (`-`). Nothing is written unless the candidate validates, compiles and every example passes the whole engine; a rejection leaves the project untouched. A document without `spec.status` is written as `proposed`: it produces no findings until a person accepts it. Decisions that may repeat it are named in the reply ("possible duplicate"), and the signals named in `provenance.wasDerivedFrom` as `signal:<id>` become recorded. The decision also needs the `local` plugin in lighthouse.toml to run in `check`.

Result: [DecisionReport](../schema/decision-report.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `document` (required) | string \| object |  | A `Decision` document, as YAML or JSON. On the command line this is a file, or `-` for stdin; the tool takes the text or the object. `metadata.name` is the id (`local/<name>`); `spec.examples` needs at least one valid and one invalid example per language the project runs. |

## decision_update

Replace a project-local decision with a Decision document.

The same gate as `decision create` applies, and nothing is written when it fails. The signals the document names in `provenance.wasDerivedFrom` become linked. A bundled decision is not changed in place: its level and options are the `rules` of lighthouse.toml, and different wording or examples are a local decision.

Result: [DecisionReport](../schema/decision-report.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `document` (required) | string \| object |  | A `Decision` document, as YAML or JSON. On the command line this is a file, or `-` for stdin; the tool takes the text or the object. `metadata.name` is the id (`local/<name>`); `spec.examples` needs at least one valid and one invalid example per language the project runs. |

## decision_signals

List the session signals: what the hooks heard of design decisions.

The hooks classify each prompt of a person (directive, correction, preference, none, or an abstention when no rule decides) and record the findings an agent's edits introduced or resolved, locally and never in git. By default the open signals that state a decision are listed; --all lists every one. The counts are by class, by rule that fired, by abstention and by status, and the measures of the loop are the share of signals recorded or linked, of proposals named a possible duplicate and of proposals a person accepted, each with a Wilson 95% interval. Retention and whether the agent is told are `[signals]` in lighthouse.toml.

Examples:
  lighthouse decision signals
  lighthouse decision signals --all --limit 50 --format json
  lighthouse decision signal dismiss 3fa9c1e --reason 'a request, not a rule'

Result: [DecisionSignals](../schema/decision-signals.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `all` | boolean | `false` | Include every signal: the settled ones, the prompts no rule decided and the findings of edits. By default, the open signals that state a decision. |
| `limit` | integer \| null | `null` | List at most this many signals and say how many were left out. |

## decision_signal_dismiss

Dismiss a signal: it is not a design decision.

A dismissed signal stays in `decision signals --all` with its reason and who gave it, and is not asked about again. The reason is the label that a later evaluation of the classifier learns from. The signal id is the one `decision signals` shows, or a unique prefix of at least 7 characters.

Examples:
  lighthouse decision signals
  lighthouse decision signals --all --limit 50 --format json
  lighthouse decision signal dismiss 3fa9c1e --reason 'a request, not a rule'

Result: [SignalDismiss](../schema/signal-dismiss.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `attributedTo` | string \| null | `null` | Who this is attributed to: `person` or `agent`, with an id after a colon (`agent:claude`). Default: the person from `git config user.name` on the command line, the client's name through MCP. |
| `id` (required) | string |  | The signal, by id or by a unique prefix of at least 7 characters. |
| `reason` (required) | string |  | Why the signal is not a decision. It labels the classifier's answer. |

## decision_eval

Measure a decision's check against its labels.

Reports precision, FPR, recall, FNR, selector precision and coverage, each with a Wilson 95% interval; the Brier score, ECE and AUROC of the probabilities models gave, with how many subjects they answered; the model calls and their cost, and a verdict against the decision's evaluation policy (`rules."<id>".evaluation`). With --check, a candidate decision file is measured beside it and their agreement is reported. Labelled positives come mostly from flagged findings, so recall is an upper bound; --audit writes unflagged selected subjects for a person to label.

Examples:
  lighthouse decision eval design/prefer-method
  lighthouse decision eval design/prefer-method --check candidate.yaml --format json
  lighthouse decision eval design/prefer-method --repo cel=../cel --audit 50

Result: [DecisionEval](../schema/decision-eval.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `audit` | integer \| null |  | Write this many selected subjects the check did not flag to a table for a person to label (`TP` or `FP`), to measure recall. |
| `check` | string \| null |  | A decision file whose check is evaluated beside the current one. |
| `id` (required) | string |  | The decision, such as `design/prefer-method`. |
| `labels` | string \| null | `null` | A table of reviewed findings (`fingerprint repo location verdict`). Default: `plugins/<pack>/labels/<name>.tsv` for the decision `<pack>/<name>`, when it exists. |
| `model` | string \| null |  | A model to grade as the first layer of the decision, beside the current check: `<provider>/<model>@sha256:<hex>`. One fitted on labels is graded on those by refits that leave each fold out. |
| `repo` | string[] | `[]` | A repository the labels are about, `name=dir`, where `name` is the `repo` column of the table. Repeatable; default: this project. |

## review_resolve

Record a judgment on a finding.

`fail` means the finding is right; add --suppress with a justification to leave it in place on purpose (a SARIF `external` suppression). `pass` means the code conforms (a false positive); `notApplicable` means the decision does not apply here, a hint to narrow it. A judgment that is not `fail`, or a `fail` with a suppression, keeps the finding out of later reports while its decision and evidence stay as they are; an error is recorded but never hidden. Judgments are appended to .lighthouse/decisions.jsonl, which is meant to be committed, and never edited: a later one replaces the standing of the finding.

--seen is the `last seen` time of the finding as you read it; the judgment is refused if the finding has been seen again since.

Examples:
  lighthouse review resolve 3fa9c1e --judgment pass --reason 'the helper is generated'
  lighthouse review resolve 3fa9c1e --judgment fail --suppress 'tracked in #214'
  lighthouse review resolve 3fa9c1e --judgment notApplicable --attributed-to agent:claude

Result: [ReviewResolve](../schema/review-resolve.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `attributedTo` | string \| null | `null` | Who this is attributed to: `person` or `agent`, with an id after a colon (`agent:claude`). Default: the person from `git config user.name` on the command line, the client's name through MCP. |
| `fingerprint` (required) | string |  | A fingerprint, or the start of one (at least 7 characters). |
| `judgment` (required) | pass \| fail \| notApplicable |  | `fail`: the finding is right. `pass`: the code conforms. `notApplicable`: the decision does not apply here. |
| `reason` | string \| null |  | Why, written for the next reader. |
| `seen` | string \| null |  | The `last seen` time of the finding as you read it (its `seen` evidence); refuses the judgment if the finding has been seen again since. |
| `suppress` | string \| null |  | With `fail`: why the finding stays, recorded as an external suppression that keeps it out of later reports. |

## model_train

Fit a model on the labels of a decision.

The labels are the rows of the labels table, the judgments recorded under its current meaning version, and optionally the answers of another model; the decision's examples ride in the question. Writes the dataset under `.lighthouse/datasets/` and the model under `.lighthouse/models/`, named by its digest; it binds nothing (bind `local/learned@sha256:<hex>`).

Examples:
  lighthouse model train design/prefer-method
  lighthouse model train design/prefer-method --model local/learned --repo cel=../cel
  lighthouse model train design/prefer-method --from-model openai/gpt-5 --format json

Result: [ModelTrain](../schema/model-train.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `fromModel` | string \| null |  | Also label the subjects nobody labelled with this model's answers (weight 0.5): a fail where it is sure of one, a pass where it is sure of the other. `<provider>/<model>`. |
| `id` (required) | string |  | The decision whose labels the model learns, such as `design/prefer-method`. |
| `labels` | string \| null | `null` | A table of reviewed findings (`fingerprint repo location verdict`). Default: `plugins/<pack>/labels/<name>.tsv` for the decision `<pack>/<name>`, when it exists. |
| `model` | string \| null |  | The model to train, `<provider>/<model>`. Default: the one bound to the decision. |

## model_attach

Make a model the first layer of a decision, by a revision.

Grades the model as `decision eval --model` does and appends a `Revision` to the decision log only when it meets the evaluation policy, loses no recall, newly fails none of the decision's examples that should pass, and decides a labelled subject the check leaves for review. Otherwise it exits 1 with the reasons and writes nothing; there is no way to force it. The next `check` asks the model first.

Examples:
  lighthouse model attach design/prefer-method --model local/learned@sha256:3f2a9c1e
  lighthouse model attach design/prefer-method --model local/learned@sha256:3f2a9c1e --repo cel=../cel
  lighthouse model attach design/prefer-method --model local/learned@sha256:3f2a9c1e --attributed-to agent:claude --format json

Result: [ModelAttach](../schema/model-attach.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `attributedTo` | string \| null | `null` | Who this is attributed to: `person` or `agent`, with an id after a colon (`agent:claude`). Default: the person from `git config user.name` on the command line, the client's name through MCP. |
| `id` (required) | string |  | The decision the model judges, such as `design/prefer-method`. |
| `labels` | string \| null | `null` | A table of reviewed findings (`fingerprint repo location verdict`). Default: `plugins/<pack>/labels/<name>.tsv` for the decision `<pack>/<name>`, when it exists. |

## config_show

Show the effective environment: models, providers, bindings, fix, sandbox.

Meaning is the project's alone (`lighthouse.toml`); how this machine computes and applies is read from, in order, the bundled defaults, the project, your file (`$XDG_CONFIG_HOME/lighthouse/config.toml`, default `~/.config/lighthouse/config.toml`) and the repository-local `.lighthouse/local.toml`. A later layer wins key by key; a provider is replaced whole. Shows each key that has a value, sorted; --origin names the layer each value comes from, as `git config --show-origin` does. The values a provider passes to its program (`env`) are hidden.

Examples:
  lighthouse config show
  lighthouse config show --origin
  lighthouse config show --origin --format json

Result: [ConfigShow](../schema/config-show.schema.json).

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `origin` | boolean | `false` | Name, for each key, the layer its value comes from: `bundled`, or the file. |
