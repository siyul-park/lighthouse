# Agents

Lighthouse reaches a coding agent three ways that share one rule system: an MCP
server (tools and resources the agent calls), hooks (the agent's harness calls
Lighthouse after edits and at the end of a turn), and a skill (the workflow and
principles, generated from the catalog and config).

## Setup

```sh
lighthouse init --agent claude-code
```

An explicit opt-in. It writes a default `lighthouse.toml` when there is none
(an existing one is kept) and merges, never overwrites:

- `.mcp.json`: `mcpServers.lighthouse = { command: "lighthouse", args: ["mcp"] }`.
  An entry you already named `lighthouse` is kept.
- `.claude/settings.json`: a `PreToolUse` group and a `PostToolUse` group (both
  with the matcher `Edit|Write|MultiEdit`) running `lighthouse hook claude-code
  pre-tool-use` and `lighthouse hook claude-code post-tool-use --allow-incomplete`,
  and a `Stop` group running `lighthouse hook claude-code stop --allow-incomplete`.
  A `UserPromptSubmit` group and a `SessionStart` group (no matcher) run `lighthouse
  hook claude-code user-prompt-submit` and `lighthouse hook claude-code session-start`.
  Groups that already run a `lighthouse hook claude-code` command are left alone.
- `.claude/skills/lighthouse/SKILL.md`: the generated skill. A file without the
  `generated by lighthouse` marker is yours and is kept.

It prints what changed and what it left alone, and a second run changes nothing.
Files are written atomically (a uniquely named temporary file, flushed, then
renamed) and a file that is a symlink is refused, not followed or replaced. JSON
files are rewritten with sorted keys when something is added: insertion order
is not kept, because enabling serde_json's `preserve_order` would change the
hashes behind meaning versions and expire stored judgments. Without `--agent`,
`init` is unchanged. `lighthouse` must be on the agent's `PATH`. The generated
hooks carry a `timeout` (120 s before and after an edit, 300 s at Stop, 10 s for
the prompt and session hooks).

## MCP server

`lighthouse mcp` serves MCP on stdio for the project found upward from the
working directory. Config, local rules and the catalog are read on every call,
so a rule just created is live at once. Tool failures are MCP tool errors
(`isError`) with a message to act on. `check` never calls an incomplete run
clean: `status` is `incomplete` whenever something was not analyzed. `paths` are
canonicalized and must lie under the project root; `diff` must be a git ref (a
value starting with `-` is refused).

A tool is named by the path of its command joined by `_`, takes the command's long
flags in camelCase with the same defaults, and returns the command's `--format json`
output as `structuredContent` (validated by the tool's `outputSchema`, the schema
`lighthouse schema <Kind>` prints) with the same JSON in a text block. Each tool has a
`title`, a `description` and `annotations` (`readOnlyHint`, `destructiveHint`,
`idempotentHint`, `openWorldHint`). An unknown tool is a JSON-RPC error. The tools:

| Tool | CLI twin | Result |
| ------ | ---------- | -------- |
| `check` | `check` | `CheckReport`: compact groups findings by decision, `detail: "full"` gives one record each |
| `fix` | `check --fix` | `FixReport`: `diff`, `applied`, `declined`, `rounds` |
| `decision_list` | `decision list` | `DecisionList` |
| `decision_show` | `decision show` | `DecisionShow`: the decision rendered as Markdown |
| `decision_create`, `decision_update` | `decision create`, `decision update` | `AuthorReport` |
| `decision_test` | `decision test` | `TestReport` |
| `decision_eval` | `decision eval` | `EvalReport` |
| `review_list` | `review list` | `ReviewList` |
| `review_show` | `review show` | `Finding`: one finding in full |
| `review_resolve` | `review resolve` | `ResolveReport` |
| `review_history` | `review history` | `JudgmentHistory` |
| `model_list`, `model_train` | `model list`, `model train` | `ModelList`, `TrainReport` |

The arguments, defaults and descriptions of each tool are in [mcp.md](mcp.md), and the
flags of the CLI in [cli.md](cli.md); both are generated from the definitions, so they
cannot drift. `review prune`, `cache clean`, `spec validate`, `schema`, `docs`, `init`,
`trust`, `mcp`, `hook` and `completions` are not tools.

Every key an agent reads or writes is lowerCamelCase: the arguments (`dryRun`,
`unsafeFixes`), the results (`lastSeen`, `catalogError`, `endLine`) and the
`check --format json` records. The contents of `evidence`, `facts` and
`options` are data and keep their names: option names are the decision's own, and the
code-model facts keep the snake_case of the plugin protocol (`max_nesting`), which
external plugins already speak (see [plugin-protocol.md](plugin-protocol.md)).

### Compact output

`check`, `review_list`, `lighthouse check --format json` and the hooks
share one token-lean shape (`--detail full`, or `detail: "full"`, gives the
per-finding records instead; the text and SARIF formats are unchanged).
Findings are grouped by decision and severity, errors first, then larger groups:

```json
{"status":"findings","counts":{"error":0,"warn":2,"review":2},
 "groups":[{"decision":"design/exported-doc","severity":"warn","review":true,
   "requirement":"<one line>","expected":"<excerpt, once>",
   "evidence":{"keys":"identical across the group"},
   "files":{"bar/bar.go":[["3:1","message","a1b2c3d"],["5:6","message","e4f5a6b",{"varying":"evidence"}]]}}],
 "resolve":"review_resolve {fingerprint, judgment, suppress?, reason?}","judgments":{}}
```

An instance is `[line:col, message, fingerprint prefix]` plus, when anything
applies, a fourth object with separate slots: `evidence` (what varies within the
group), `note` (why a judgment did not hide the finding) and `review`
(true on an instance that asks for review, only in a group where some do and
some do not; the group's own `review` is true when any does). The prefix is the
shortest unique one among the findings of the report, at least 7 characters;
`review_resolve`, `review_show`, `fix` and `lighthouse review resolve` accept it. Recorded
findings the report did not show can share the prefix: an ambiguous prefix is
refused with a message to retry with a longer prefix, listing up to five
candidate full fingerprints. The symbol
is evidence unless the message names it; `authored` appears on a group only when
it differs from the severity; `context` is left to `decision_show`. `limit` counts
findings (default 25 for `check`, 50 for `review_list`) and what is cut is in
`omitted`. The hooks print a header per group (`decision severity [review] -
requirement`), `expected:` once, then `path:line:col message fingerprint` per
finding, the gaps, `resolve:` and `reasons:` once, and the summary.

### Fixes in a report

A check marks what is fixable and computes no fix: it costs one analysis, and the
diff of a fix belongs to the run that verifies it (`fix` with `dryRun`,
`check --fix --dry-run`, or the previews a run leaves under `ask`), so a finding
never shows two different diffs. No format of `check` carries a diff, and its
SARIF has no `fixes`. `check --fix --format sarif` is the fix run's report: the
findings of the project, and as `result.fixes` (`artifactChanges` with
`replacements` of regions) the verified previews the run left, and in a
`--dry-run` every fix it would make, from every provider; a fix that was written
or declined has none.

- A group of a fixable decision has `fix`, which says who fixes (`cel`,
  `command`, `rpc`, `model`), the safety, whether it runs (and `why` when it
  does not), whether an `unsafe` fix is `written` or only previewed, and `apply`:
  `lighthouse check --fix --decision <id>` or the `fix` tool call
  `fix {"decision":["<id>"]}`. That step writes a `safe` fix and previews an
  `unsafe` one, unless `[fix] unsafe` is set; each preview then carries its diff and its own
  `apply`, with `--unsafe-fixes` and the fingerprints of every finding the same
  run of the fix was made for. A decision with no fix, an `unsafe` one or one that does not run
  has `brief: true`: `review_show` has the brief to fix the finding by hand.
- SARIF columns count UTF-16 code units, as SARIF defines them, so locations
  on lines with multibyte characters are converted from the byte columns of
  the code model.

Prefer `check --fix` for safe fixes, and read the diff before applying
unsafe ones: a preview is applied by its fingerprint (`check --fix
--unsafe-fixes --fingerprint <fp>`, or the `fix` tool with `fingerprints` and
`unsafeFixes`).

### Fixing

`fix` applies the fixes that the catalog attaches to rules (`fix` in
`decision_list` and `decision_show`, `fixable: safe|unsafe` in the skill; see "Fixing" in
[architecture.md](architecture.md)). Name what to fix with `fingerprints` (from
`check`; prefixes are accepted), `paths` (under the project root) or `decision`: a
fix never defaults to the whole project. Use `dryRun` first: it returns the
`diff` and leaves every file as it was. Only safe fixes are applied unless
`unsafeFixes` is true or the project allows it (`[fix] unsafe = true`; `unsafeFixes: false` overrides it for one call); unsafe ones
are then judgment calls to review in the diff, and without it they come back in
`previews` with their diff, whatever program makes them. `noModels` asks no model. Every applied fix has been re-checked together with the safe fixes of
what it introduced (the formatter's among them) and, for a file that gained an error or stopped
being analyzable, rolled back, so `declined` also says what was undone and why.
Findings that a judgment hides are never fixed, and a run refuses to start
while the analysis is incomplete. Commands run only in a project the user trusted with
`lighthouse trust`, and without trust a command fix is declined. Trust is the user's, given at a terminal: `lighthouse trust` lists the
commands and asks (`--yes` only after reading the list), and `init --agent claude-code`
adds `Bash(lighthouse trust:*)` to the project's permission deny list so the agent cannot
trust a project for you. A project that needs trust to be checked (it lists a plugin it brings,
or turns the sandbox off) and does not have it is a state, not a failure: the hooks that check
(PreToolUse, PostToolUse, Stop) tell the session once, as context that does not block, that
Lighthouse is not checking and why, exit 0 and stay silent for the rest of that session; the
prompt and session-start hooks work as before. Nothing is written until the whole run verified in memory, and
a file that changed meanwhile is skipped and reported, with every file of a fix that
spans it. The findings the fixes removed
are resolved by the run that ends the fixing. Recheck with `check` afterwards.

### Resources

- `lighthouse://decisions/{id}`: one decision rendered as Markdown (the id keeps its
  slash: `lighthouse://decisions/design/exported-doc`).
- `lighthouse://catalog`: `id`, authored severity and title of every decision, tab separated.
- `lighthouse://config`: root, plugins, `extends`, the active rule ids and the
  `lighthouse.toml` text.

### Reviewer identity

Every judgment recorded through the server is attributed to a `SoftwareAgent`. The id is
`attributedTo` (`agent:<id>`), else `$LIGHTHOUSE_ATTRIBUTED_TO`, else the name the
client sent in `clientInfo` at `initialize`, else `mcp-agent`. The CLI keeps its own rule
(`--attributed-to person|agent[:<id>]`, `$LIGHTHOUSE_ATTRIBUTED_TO`, then the person
configured for the repository or `$USER`).

### Authoring decisions

`decision_create` takes a `document`: a `Decision` as an object or YAML/JSON text (on
the command line, `lighthouse decision create <FILE|->`). `metadata.name` is the id
(`local/<name>`); `spec` holds the title, context, `scope: {subject}`, requirement
with MUST or SHOULD, severity, a `check` of `type: cel` with `select`, `where` as a
CEL expression that is true for a violation, `message` and `evidence`, and the
examples (at least one valid and one invalid per language the project runs).
The candidate is validated, compiled and tested through the whole engine before
anything is written, to `.lighthouse/decisions/<name>.yaml`; a failure names the
example and writes nothing. `decision_update` takes the whole document of an existing
local decision and replaces it through the same gate. A bundled decision is not
changed in place: its level and options are the `rules` of `lighthouse.toml`, and
different wording or examples are a local decision.
Decision names are lowercase letters, digits, `.`, `_` and `-` (no `/`, `\` or
`..`), checked before anything else runs, and authoring takes a per-project
lock (`.lighthouse/authoring.db-lock`, ignored by version control) around its
read-modify-write. The `local` plugin must be listed in `lighthouse.toml` for
`check` to run local decisions; the result says when it is not.

Example:

```json
{ "name": "decision_create", "arguments": { "document": {
  "kind": "Decision",
  "metadata": { "name": "local/short-notes" },
  "spec": {
    "title": "Notes stay short",
    "context": "Notes are read at a glance.",
    "scope": { "subject": "file" },
    "requirement": "A note file MUST NOT exceed three lines.",
    "severity": "error",
    "check": { "type": "cel", "select": "file", "where": "file.lines > 3",
               "message": "{{ file.path }} is too long", "evidence": { "path": "file.path" } },
    "examples": [
      { "name": "long", "language": "text", "kind": "invalid",
        "files": [{ "path": "a.txt", "body": "a\nb\nc\nd\n" }], "expect": [{ "line": 1 }] },
      { "name": "short", "language": "text", "kind": "valid",
        "files": [{ "path": "a.txt", "body": "a\n" }] } ] } } } }
```

## Hooks (Claude Code)

`lighthouse hook claude-code <event> [--allow-incomplete]` reads the hook payload
on stdin, enters its `cwd`, decides the report scope, runs the check and answers
in Claude Code's format. The hook is dumb: what is a finding, and what blocks,
is Lighthouse's judgment. **A hook never fixes**: it reports, and the agent or
the user decides to run `fix` or `check --fix`; a hook that rewrote files under
an editing agent would change the code the agent is reading. A directory without `lighthouse.toml` is left alone
(silent, exit 0).

Contract used (Claude Code hooks reference): the payload has `session_id`, `cwd`,
`hook_event_name`, and for PreToolUse and PostToolUse `tool_name` and
`tool_input.file_path`; for UserPromptSubmit `prompt`; for SessionStart `source`;
for Stop `stop_hook_active`. Output is exit 0 with a JSON object on stdout:
`decision: "block"` plus `reason` is fed back to the agent (after PostToolUse the
edit already happened; at Stop it keeps the agent working),
`hookSpecificOutput.additionalContext` adds context without blocking, and
`systemMessage` shows the user a note. Exit 2 is never used, so a failing hook
cannot block the agent: payload or internal errors exit 1, which Claude Code
treats as non-blocking.

**The session baseline.** The hooks report what the session introduced, not what
was already there. `pre-tool-use` checks the file an edit tool is about to touch
(models off, nothing stored) and writes its findings, `{fingerprint: evidence
digest}`, to `.lighthouse/cache/hooks/<session_id>/<hash of path>.json`, once per
file and session: a later touch keeps the state from before the first edit, and a
file that does not exist yet gets an empty baseline. It prints nothing and never
blocks; a failure goes to stderr and exits 1. The other two events keep the
findings that are `new` (fingerprint not in the baseline) or `updated` (same
fingerprint, different evidence digest), the SARIF `baselineState`s; `unchanged`
ones are not reported. Session directories older than 7 days are deleted when a
baseline is written. A `session_id` that is not `[A-Za-z0-9_-]{1,128}` is no
session.

| Event | Scope | Behavior |
| ------- | ------- | ---------- |
| `pre-tool-use` | the file to be touched (`Edit`, `Write`, `MultiEdit` only) | records the baseline if the session has none for the file; silent |
| `post-tool-use` | the edited file (`Edit`, `Write`, `MultiEdit` only) | new or updated error or warn findings: `decision: block` with up to 5 findings in the text form of the findings; new or updated info findings that ask for review only: `additionalContext` with the count and how to resolve them through MCP; incomplete analysis is stated and, without `--allow-incomplete`, blocks; nothing new and complete: silent. Without a session or a baseline for the file, every finding of the file is reported with a note that the PreToolUse hook is missing |
| `stop` | the files with a baseline in the session that still exist | new or updated errors, or an incomplete analysis (with or without `--allow-incomplete`; the flag only changes the wording), block once with up to 10 findings and the gaps; otherwise allowed, with a `systemMessage` when new warnings, infos, findings asking for review or gaps remain. No baseline in the session, or no session: silent, and no check runs |

| `user-prompt-submit` | the prompt | classified by the `decision-signal` rules and recorded as a signal, whatever the class (see below); with `[signals] surface = "on"` and a directive, correction or preference, `additionalContext`: "this reads like a design decision", up to 3 existing decisions that may already say it, and how to record or link it. Runs no check and starts no provider; never blocks |
| `session-start` | the project | with surfacing on, `additionalContext`: up to 6 accepted decisions in force and the proposals waiting for a person, one line each, with how they were ranked; silent in shadow. Runs no check and starts no provider |

Not covered: edits made through Bash (`sed`, scripts) are not tracked, so Stop
scopes to the files the edit tools touched. The MCP `check` tool is an explicit
request and keeps the scope of its arguments; pass `changed` or paths for a
session scope.

Failures are never silent. Only a directory with no `lighthouse.toml` gets
silence. A broken config, broken local rules or a plugin that cannot start are
told to the agent ("nothing was checked, this is not a pass") with the error: as
`additionalContext` after an edit, and as one block at Stop (a forced stop only
gets a `systemMessage`).

Each hook run analyzes the whole project (the scope only narrows the report),
so its cost grows with the project and with the language plugins it starts; the
`timeout` bounds it, and `--allow-incomplete` keeps a slow or failing plugin from
trapping a session. The fast path skips, before any plugin starts, a file that does not exist, lies
outside the project, is under `.git`, `.lighthouse` or `node_modules`, or is
binary. Analysis always covers the whole project, so the scope only narrows the
report. The loop guard: when `stop_hook_active` is true the stop is never blocked
again; the user gets a `systemMessage` instead. The hook records the run in the
store like `check` does and records no judgments, so the reviewer kind does not
come into play.

### Signals

What a session says about design decisions is recorded as **signals**, in the
local store (`.lighthouse/lighthouse.db`), never in git and never in the decision
log. Only the decisions an agent records are committed.

- **From prompts.** The `user-prompt-submit` hook cuts out what is not the
  person's words (code blocks, pastes, quoted and log lines, URLs),
  splits the rest into sentences and matches the rules of the `decision-signal`
  classifier (a table in ko and en, `crates/lighthouse-session/src/signal/rules.toml`;
  questions never match). The class is `directive`, `correction`, `preference`,
  `none` (an acknowledgement) or `abstain` (no rule decides). An abstention is meant to fall
  through the classification binding layers (`[models] classification`), but a
  model layer for free-text classes is a later wave: the existing classification
  task answers P(fail) per decision, and these hooks run no provider. Until then
  an abstention stays one. Every prompt is recorded with the class, the rule that fired, a
  scrubbed excerpt of at most 200 characters (the sentence a rule fired on, else
  the start of the message) and features that are not text (language, size,
  whether code or pasted content was cut).
- **From edits.** The findings an edit introduced or resolved, which the
  baseline already computes, are recorded by `post-tool-use` and `stop` as class
  `finding`, attributed to the agent, once each.
- **Scrubbing and retention.** Before anything is stored the excerpt passes the
  secret patterns of `lighthouse-signal` (provider tokens, private keys, bearer
  tokens, credentials in URLs, secret-looking assignments). Signals older than
  `[signals] retention` (default `30d`) are purged when a new one is written.
- **Surfacing.** `[signals] surface = "shadow"` (the default) records and prints
  nothing to the agent. `"on"` also tells it: the prompt context above, the
  session digest, and at `stop` one review task for the open signals not asked
  about yet ("record, link or dismiss each"), never when `stop_hook_active` is
  set. Turn it on only after the recorded prompts were labelled and the
  precision shown.
- **Settling.** `decision_create` with `provenance.wasDerivedFrom:
  ["signal:<id>"]` makes the signal `recorded`; `decision_update` naming it makes
  it `linked`; `decision signal dismiss <id> --reason …` (MCP
  `decision_signal_dismiss`) dismisses it. A decision created without an
  explicit `spec.status` is `proposed`: it produces no findings until a person
  accepts it. The reply of `decision_create` names decisions that may repeat it
  ("possible duplicate"; SQLite FTS5 `bm25()` over the decisions' text with the
  `trigram` tokenizer, similarity from 0 to 1, threshold 0.7, set conservatively and to be tuned on collected data); the
  decision is written anyway.
- **Looking.** `decision signals` (MCP `decision_signals`) lists the open
  signals and gives the counts by class, rule, abstention and status, and the
  measures of the loop (signals recorded or linked, proposals named a possible
  duplicate, proposals a person accepted), counted from statuses and from
  `decision_create` calls, each with a Wilson 95% interval. `decision show` of a
  proposal gives its support: its signals by class and attribution, and the
  share a person made, smoothed with a uniform Beta prior.

## Skill

The skill is generated, never hand-written: purpose (decision memory), the loop
(check, understand, fix, recheck, judge with reasons), rules of conduct (never
suppress a mechanical finding except through an annotated exception with a
reason), how to look rules up (resources and `decision_show`, not the rule text), and
a digest of the active decisions (id, authored severity, title). `lighthouse docs generate`
writes `skills/lighthouse/SKILL.md` for this repository and `docs check` fails
when it is stale; `init --agent claude-code` writes the project's copy from its
own catalog and config.

The skill and `decision show` read the catalog, not running plugins. The invariant
that keeps them complete: every rule, including a future out-of-process rule
plugin, ships its decisions into the catalog, so the digest never has to start
a plugin process. Today language plugins supply only languages and every rule is
in-process; a test checks that the skill lists every rule the engine's registry
enables.
