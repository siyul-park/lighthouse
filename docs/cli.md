# Command reference

Generated by `lighthouse docs generate` from the command definitions; `lighthouse docs check` fails when it is stale.

Exit codes of every command: 0 success or nothing found, 1 findings over the threshold or a failed test, validation or docs check, 2 usage or runtime error, 3 incomplete analysis.

## `lighthouse`

```text
Design-quality linter

Usage: lighthouse [OPTIONS] <COMMAND>

Commands:
  check        Check the project and print findings
  decision     Inspect, author, test and evaluate decisions
  review       Review the findings `check` remembers and record judgments on them
  model        List, train, attach and detach the models that judge decisions
  cache        Manage the result cache in `.lighthouse/cache`
  spec         Validate spec documents
  schema       Print the JSON Schema of a kind of document or output
  docs         Generate or verify the Markdown docs derived from the code
  completions  Print the completions of a shell
  init         Write a default lighthouse.toml in the current directory
  trust        Trust this project to run the commands it names
  mcp          Serve the Model Context Protocol on stdio, for coding agents
  hook         Entry points for agent hooks. Reads the hook payload on stdin
  help         Print this message or the help of the given subcommand(s)

Options:
      --config <FILE>
          The project file; the project root is then the current directory
          
          [env: LIGHTHOUSE_CONFIG=]

      --color <COLOR>
          Color of help and messages. `auto` honours NO_COLOR and CLICOLOR_FORCE
          
          [env: LIGHTHOUSE_COLOR=]
          [default: auto]
          [possible values: auto, always, never]

  -h, --help
          Print help

  -V, --version
          Print version
```

## `lighthouse check`

```text
Check the project and print findings.

PATHS select which findings are reported, not what is analyzed: the whole project is always analyzed, because decisions and language providers need more than the reported files (callers, packages, build context).

Exit codes: 0 clean, 1 an error was found (or warnings fail the run: --strict, --max-warnings; info never does), 2 usage or runtime error, 3 the analysis was incomplete (a file could not be read or loaded, a plugin crashed or timed out). "Not checked" is never "passed"; --allow-incomplete reports it but does not fail on it.

Plugins named by the config are started and run with your privileges, like build scripts: only check projects whose config you trust. A plugin that cannot start, or that is not the protocol version or identity its entry names, is an error (exit 2); one that starts but crashes, times out or answers badly is reported as incomplete (exit 3).

Usage: lighthouse check [OPTIONS] [PATHS]...

Arguments:
  [PATHS]...
          Where to report findings; the whole project is analyzed anyway. Default: the whole project

Options:
      --changed
          Report only files changed in the working tree against HEAD (modified, added, renamed, untracked). A report filter like PATHS

      --diff <BASE>
          Report only files changed since the merge base of BASE and HEAD, including the working tree and untracked files. A report filter

      --decision <ID>
          Run only these decisions: ids, comma-separated or repeated, and globs such as `design/*`

      --limit <N>
          Report at most this many findings, errors first, and say how many were left out. Default: 25 with `--format json`, all otherwise

      --detail <DETAIL>
          With `--format json`: compact groups findings by decision and states a decision's text once; full gives one self-contained record per finding

          Possible values:
          - compact: Grouped by decision, a decision's text said once
          - full:    One self-contained record per item
          
          [default: compact]

      --no-store
          Do not record this run in `.lighthouse/lighthouse.db` and do not apply judgments. By default a run is recorded: findings it no longer reports are marked resolved (never when the analysis was incomplete), and findings whose latest judgment hides them stay out of the report

      --no-cache
          Run every rule instead of reusing the findings of earlier runs kept in `.lighthouse/cache`. The findings and the exit code are the same

      --no-models
          Ask no model: what they would judge is left to review

      --all-models
          Ask models that cost about the whole project, not only the files the run reports

      --record-model-labels
          Record what models fail as judgments attributed to them, so that training can reproduce them from `decisions.jsonl`

      --strict
          Fail on warnings too

      --max-warnings <N>
          Fail when there are more than N warnings (errors always fail)

      --allow-incomplete
          Exit by findings even when the analysis was incomplete; the incompleteness is still reported

      --format <FORMAT>
          `text`, `json` (findings grouped by decision) or `sarif`

          Possible values:
          - text:  `path:line:col: severity id: message`, one finding a line
          - json:  Findings grouped by decision, as one JSON document on one line
          - sarif: SARIF 2.1.0
          
          [default: text]

      --timings
          Print where the time went to stderr, phase by phase: reading, each language provider, merging, analyzers, the slowest rules, identity, the store and the report. Findings and exit code do not change

      --fix
          Fix what the catalog's fixers can fix, then report what is left. Only safe fixes of mechanical rules are applied; each is verified (formatted, re-checked) and a file that gets worse is rolled back. PATHS and --decision select which findings are fixed

      --dry-run
          Print the unified diff and leave every file as it was

      --unsafe-fixes
          Also apply suggested fixes, which are judgment calls: review the diff

      --fixer <ID>
          Use this registered fixer for the selected findings instead of the one their decision names. Its fixes count as suggested

  -h, --help
          Print help (see a summary with '-h')

Examples:
  lighthouse check
  lighthouse check src/ --decision 'design/*' --format json --limit 10
  lighthouse check --changed --strict
  lighthouse check --fix --dry-run --decision design/exported-doc
```

## `lighthouse decision eval`

```text
Measure a decision's check against its labels.

Reports precision, FPR, recall, FNR, selector precision, coverage and abstention, each with a Wilson 95% interval; the Brier score, ECE and AUROC of the probabilities models gave, with how many subjects they answered; the model calls and their cost, and a verdict against the decision's evaluation policy (`rules."<id>".evaluation`). With --check, a candidate decision file is measured beside it and their agreement is reported. Labelled positives come mostly from flagged findings, so recall is an upper bound; --audit writes unflagged selected subjects for a person to label.

Usage: lighthouse decision eval [OPTIONS] <ID>

Arguments:
  <ID>
          The decision, such as `design/prefer-method`

Options:
      --repo <NAME=DIR>
          A repository the labels are about, `name=dir`, where `name` is the baseline's `repo` column. Repeatable; default: this project

      --baseline <FILE>
          A table of reviewed findings. Default: `baseline/precision/<id>.tsv` when it exists

      --check <FILE>
          A decision file whose check is evaluated beside the current one

      --model <REF>
          A model to grade as the first layer of the decision, beside the current check: `<provider>/<model>@sha256:<hex>`. One fitted on labels is graded on those by refits that leave each fold out

      --audit <N>
          Write this many selected subjects the check did not flag to a table for a person to label (`TP` or `FP`), to measure recall

      --format <FORMAT>
          `text` for people, `json` for programs (its schema: `lighthouse schema`)

          Possible values:
          - text: The human form
          - json: One JSON document on one line
          
          [default: text]

  -h, --help
          Print help (see a summary with '-h')

Examples:
  lighthouse decision eval design/prefer-method
  lighthouse decision eval design/prefer-method --check candidate.yaml --format json
  lighthouse decision eval design/prefer-method --repo cel=../cel --audit 50
```

## `lighthouse review resolve`

```text
Record a judgment on a finding.

`fail` means the finding is right; add --suppress with a justification to leave it in place on purpose (a SARIF `external` suppression). `pass` means the code conforms (a false positive); `notApplicable` means the decision does not apply here, a hint to narrow it. A judgment that is not `fail`, or a `fail` with a suppression, keeps the finding out of later reports while its decision and evidence stay as they are; an error is recorded but never hidden. Judgments are appended to .lighthouse/decisions.jsonl, which is meant to be committed, and never edited: a later one replaces the standing of the finding.

--seen is the `last seen` time of the finding as you read it; the judgment is refused if the finding has been seen again since.

Usage: lighthouse review resolve [OPTIONS] --judgment <JUDGMENT> <FP>

Arguments:
  <FP>
          A fingerprint, or the start of one (at least 7 characters)

Options:
      --judgment <JUDGMENT>
          `fail`: the finding is right. `pass`: the code conforms. `notApplicable`: the decision does not apply here

          Possible values:
          - pass:          The code conforms: the finding is a false positive
          - fail:          The finding is right
          - notApplicable: The decision does not apply here; a hint to narrow it

      --suppress <JUSTIFICATION>
          With `fail`: why the finding stays, recorded as an external suppression that keeps it out of later reports

      --reason <REASON>
          Why, written for the next reader

      --attributed-to <WHO>
          Who the judgment is attributed to: `person` or `agent`, with an id after a colon (`agent:claude`). Default: the person from `git config user.name` on the command line, the client's name through MCP
          
          [env: LIGHTHOUSE_ATTRIBUTED_TO=]

      --seen <LAST_SEEN>
          The `last seen` time of the finding as you read it (its `seen` evidence); refuses the judgment if the finding has been seen again since

      --format <FORMAT>
          `text` for people, `json` for programs (its schema: `lighthouse schema`)

          Possible values:
          - text: The human form
          - json: One JSON document on one line
          
          [default: text]

  -h, --help
          Print help (see a summary with '-h')

Examples:
  lighthouse review resolve 3fa9c1e --judgment pass --reason 'the helper is generated'
  lighthouse review resolve 3fa9c1e --judgment fail --suppress 'tracked in #214'
  lighthouse review resolve 3fa9c1e --judgment notApplicable --attributed-to agent:claude
```

## `lighthouse model train`

```text
Fit a model on the labels of a decision.

The labels are the baseline rows, the judgments recorded under its current meaning version, and optionally the answers of another model; the decision's examples ride in the question. Writes the dataset under `.lighthouse/datasets/` and the model under `.lighthouse/models/`, named by its digest; it binds nothing (bind `local/learned@sha256:<hex>`).

Usage: lighthouse model train [OPTIONS] <ID>

Arguments:
  <ID>
          The decision whose labels the model learns, such as `design/prefer-method`

Options:
      --model <REF>
          The model to train, `<provider>/<model>`. Default: the one bound to the decision

      --from-model <REF>
          Also label the subjects nobody labelled with this model's answers (weight 0.5): a fail where it is sure of one, a pass where it is sure of the other. `<provider>/<model>`

      --baseline <FILE>
          A table of reviewed findings (`fingerprint repo location verdict`)

      --repo <NAME=DIR>
          A repository the labels are about, `name=dir`, where `name` is the baseline's `repo` column. Repeatable; default: this project

      --format <FORMAT>
          `text` for people, `json` for programs (its schema: `lighthouse schema`)

          Possible values:
          - text: The human form
          - json: One JSON document on one line
          
          [default: text]

  -h, --help
          Print help (see a summary with '-h')

  lighthouse model train design/prefer-method
```

## `lighthouse model attach`

```text
Make a model the first layer of a decision, by a revision.

Grades the model as `decision eval --model` does and appends a `Revision` to the decision log only when it meets the evaluation policy, loses no recall, newly fails none of the decision's examples that should pass, and decides a labelled subject the check leaves for review. Otherwise it exits 1 with the reasons and writes nothing; there is no way to force it. The next `check` asks the model first.

Usage: lighthouse model attach [OPTIONS] --model <REF> <ID>

Arguments:
  <ID>
          The decision the model judges, such as `design/prefer-method`

Options:
      --model <REF>
          The model to attach, `<provider>/<model>@sha256:<hex>` for a learned one: graded as the first layer of the decision before anything is written

      --baseline <FILE>
          A table of reviewed findings. Default: `baseline/precision/<id>.tsv` when it exists

      --repo <NAME=DIR>
          A repository the labels are about, `name=dir`, where `name` is the baseline's `repo` column. Repeatable; default: this project

      --attributed-to <WHO>
          Who approves the revision: `person` or `agent`, with an id after a colon (`agent:claude`). Default: the person from `git config user.name` on the command line, the client's name through MCP
          
          [env: LIGHTHOUSE_ATTRIBUTED_TO=]

      --format <FORMAT>
          `text` for people, `json` for programs (its schema: `lighthouse schema`)

          Possible values:
          - text: The human form
          - json: One JSON document on one line
          
          [default: text]

  -h, --help
          Print help (see a summary with '-h')

Examples:
  lighthouse model attach design/prefer-method --model local/learned@sha256:3f2a9c1e
  lighthouse model attach design/prefer-method --model local/learned@sha256:3f2a9c1e --repo cel=../cel
```

## `lighthouse model rebuild`

```text
Make the missing artifacts of attached models again, from their labels.

A learned model is a file named by its digest and kept out of git; a fresh clone has the revision that attached it and not the file. Per attached model the status is `present` (the file is what its name says), `rebuilt` (training made it again, bit for bit), `differs` (a file or a training run gives another digest; nothing is deleted), `labels-changed` (the labels are no longer those it was attached with; nothing is trained), `not-rebuildable` (its trainer is not deterministic or does not learn) or `not-local` (a service, not a file). Exits 1 unless every model is `present`, `rebuilt` or `not-local`.

Usage: lighthouse model rebuild [OPTIONS] [ID]...

Arguments:
  [ID]...
          Decisions or globs such as `design/*`; default: every decision with an attached model

Options:
      --baseline <FILE>
          A table of reviewed findings, for the labels when the dataset the model was attached with is gone

      --repo <NAME=DIR>
          A repository the labels are about, `name=dir`, where `name` is the baseline's `repo` column. Repeatable; default: this project

      --format <FORMAT>
          `text` for people, `json` for programs (its schema: `lighthouse schema`)

          Possible values:
          - text: The human form
          - json: One JSON document on one line
          
          [default: text]

  -h, --help
          Print help (see a summary with '-h')

Examples:
  lighthouse model rebuild
  lighthouse model rebuild 'design/*' --repo cel=../cel
  lighthouse model rebuild design/prefer-method --format json
```

## `lighthouse trust`

```text
Trust this project to run the commands it names.

Command fixers and the formatters of `lighthouse.toml`. Trust is yours, kept in `$XDG_CONFIG_HOME/lighthouse/trust.toml` (default `~/.config/lighthouse/trust.toml`) for this root and the exact `lighthouse.toml` and `.lighthouse/decisions` you have read; a change to either withdraws it. `LIGHTHOUSE_TRUST=1` trusts every project, for CI. Without trust a command fix is declined and formatting is skipped; checks and the verification of fixes still run.

It lists the formatters and fixer commands it would trust and asks for confirmation on the terminal; without a terminal it refuses unless `--yes` says you have read the list.

Usage: lighthouse trust [OPTIONS]

Options:
      --revoke
          Withdraw the trust instead

      --yes
          Trust without asking; for scripts, after reading what is listed

  -h, --help
          Print help (see a summary with '-h')
```
